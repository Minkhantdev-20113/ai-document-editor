Phase 3 goal:
Implement the production-grade BYOK AI provider system and intelligent multi-key failover.

This phase is extremely important.

Historical failure:
A previous implementation had multiple API keys but they became exhausted very quickly.

Do NOT solve this by simply rotating keys sequentially.

KEY PRINCIPLE:

Multiple API keys do NOT necessarily mean multiplied provider quota.

Provider limits can exist at:
- API key
- project
- account
- organization
- model
- IP
- RPM
- TPM
- RPD
- TPD
- other provider-specific levels

The application must detect and respect these limits.

PROVIDER ARCHITECTURE

Create a common provider interface.

Conceptually:

AIProvider
 ├── GeminiProvider
 ├── GroqProvider
 ├── OpenRouterProvider
 ├── DeepSeekProvider
 └── OpenAICompatibleProvider

Each provider adapter must expose:

- validateKey()
- listModels()
- getCapabilities()
- estimateTokens()
- generate()
- translate()
- getUsage()
- getRateLimitState()
- classifyError()

Do not scatter provider-specific logic across UI components.

KEY SELECTION

Implement:

Health-aware weighted scheduling.

Do NOT use simple round-robin.

Before selecting a key consider:

- enabled
- valid
- cooldown
- recent failures
- recent 429
- provider health
- model support
- estimated token requirement
- known RPM
- known TPM
- local usage estimate

RATE LIMIT HANDLING

Correctly classify:

- 429
- quota exceeded
- insufficient quota
- authentication error
- invalid API key
- invalid model
- network error
- timeout
- server error
- content policy error

For 429/rate-limit errors:

1. Save error.
2. Read Retry-After if available.
3. Read provider rate-limit headers if available.
4. Set cooldown.
5. Select another healthy candidate only if doing so is valid.
6. Otherwise wait.
7. Exponential backoff with jitter.
8. Never create a tight retry loop.

IMPORTANT:

If all keys share an upstream account/project quota, do NOT endlessly rotate keys.

Instead show:

"Provider quota exhausted"

and pause the affected job safely.

JOB RESUMPTION

If a key fails during translation:

- never lose completed translation units
- save the current unit state
- retry using another valid key/provider
- resume from the failed unit

TRANSLATION BATCHING

Do NOT send an entire PDF as one huge AI request.

Create controlled batches.

Batch size must depend on:

- model context
- estimated tokens
- provider limits
- document type
- target language
- translation quality requirements

For Burmese translation:

Preserve:
- technical terminology
- numbers
- units
- formulas
- code
- citations
- URLs
- proper nouns when appropriate
- Markdown/structure markers

Use structured JSON responses whenever supported.

Do not accept uncontrolled prose when structured output is possible.

API KEY SECURITY

- Never send raw keys to Google Sheets.
- Never log raw keys.
- Never expose keys in URLs.
- Never place keys in source code.
- Never place keys in Vite environment variables if the application is intended to distribute the frontend publicly.
- Build a local key vault abstraction.

Because this is BYOK, explain in the UI that browser-side API keys are controlled by the user and should only be used with keys the user is comfortable using from a client application.
